## 1. Что мы строим

Онлайн-казино на виртуальные монеты:

- 2–4 игрока в комнате;
- три игры: блэкджек, дурак, кости;
- Telegram-бот и веб-сайт используют **один аккаунт и один кошелёк**;
- вход на сайт по одноразовому коду из Telegram;
- админка: игроки, балансы, донаты, выводы, комнаты, режим работы;
- всё запускается одной командой `python bot/main.py` или Docker.

Главный принцип, который нужно понять до первой строки кода:

> **Сервер — единственный источник правды. Клиент присылает только намерение.**

Клиент никогда не говорит «у меня 6 на кубике» или «зачисли мне 1000 монет».
Он говорит «я бросаю кубик» / «создай заявку на вывод». Сервер сам проверяет ход,
генерирует случайность, списывает ставку, считает результат и рассылает состояние.

Если этот принцип нарушить, игру можно взломать из консоли браузера за пять минут.

## 3. Ментальная модель: событие, состояние, ответ

Любое действие в игре — это короткий цикл:

```
1. Клиент отправляет событие        socket.emit("playerAction", { action: "roll" })
2. Сервер находит комнату и игрока  rooms.get(socket.data.roomId)
3. Проверяет право на действие      ваш ли ход? не бросали ли уже?
4. Меняет состояние                 room.diceRolls[player.id] = crypto.randomInt(1, 7)
5. Сохраняет в SQLite               saveRoom(room)
6. Рассылает всем новое состояние   broadcastRoom(room)
7. Клиент перерисовывает UI         setRoom(state)
```

Запомните этот цикл — дальше все файлы раскладываются по его шагам.

### Почему не REST для игры

REST хорошо подходит для «прочитать профиль» или «создать заявку». Для игры нужен
**push**: сервер сам сообщает всем игрокам, что ход изменился. Поэтому здесь
Socket.io: он держит постоянное соединение и умеет комнаты (`socket.join(roomId)`).

REST остаётся для:

- входа по коду (`/api/auth/login`);
- истории и статистики;
- донатов и выводов;
- админки.

## 4. Жизненный цикл запроса на примере комнаты

Смотреть в коде: `casino/server.js`, обработчик `io.on("connection")` → `socket.on("join")`.

### Шаг 1. Подключение

```js
io.on("connection", (socket) => {
  console.log(`🔌 connected ${socket.id}`);
  // ...
});
```

Сокет — это конкретная вкладка браузера. Один игрок может открыть две вкладки —
это два сокета. Поэтому в комнате хранят `connected` у игрока, а не «один сокет =
один игрок».

### Шаг 2. Вход в комнату

```js
socket.on("join", async (data = {}) => {
  const sessionUser = await resolveSession(data.sessionToken);
  const rawUserId = sessionUser ? sessionUser.id : data.userId;
  const user = await ensureUser(rawUserId, name);
  const userId = user.id;
  // ...
});
```

Важная деталь: **если есть токен сессии, `userId` из клиента игнорируется**.
Иначе любой мог бы прислать чужой Telegram ID и играть за чужой кошелёк.

Если игрок уже был в другой комнате, сервер сначала корректно выходит из неё:

```js
if (socket.data.roomId && socket.data.roomId !== requestedRoomId) {
  await leaveRoom(socket);
}
```

### Шаг 3. Создание или поиск комнаты

```js
if (requestedRoomId && rooms.has(requestedRoomId)) {
  room = rooms.get(requestedRoomId);       // вход по коду
} else if (requestedRoomId && !rooms.has(requestedRoomId)) {
  emitError(socket, "Комната не найдена");
  return;
} else {
  const roomId = generateRoomId();
  room = new Room(roomId, { gameType, bet, maxPlayers, creatorId: userId });
  rooms.set(roomId, room);                  // новая комната
}
```

Комнаты живут в памяти (`Map`), но каждая сохраняется в SQLite. Память — для
скорости, SQLite — чтобы пережить перезапуск.

### Шаг 4. Ответ и рассылка

```js
socket.join(room.id);
socket.data.roomId = room.id;
socket.emit("joined", { roomId: room.id, userId, isCreator });
broadcastRoom(room);
```

`broadcastRoom` отправляет **каждому сокету персональный снимок**:

```js
socket.emit("roomUpdated", room.toJSONFor(socket.data.userId));
```

Почему персональный? Потому что чужие карты в блэкджеке показывать нельзя.
`toJSONFor(viewerId)` скрывает `hand` и `score` других игроков, пока партия не
закончена.

> 🎬 Посмотрите шаги 1–4 в анимации: [`assets/backend-demo.html`](assets/backend-demo.html).

## 5. Деньги: как не потерять и не напечатать лишнего

### 5.1. Одна таблица `users`, поле `balance`

Все балансы — целые числа в одной таблице. Никаких `float` для денег: `0.1 + 0.2`
в JavaScript не равно `0.3`, а в игре на тысячах операций это превращается в
расхождения.

### 5.2. Каждая операция — транзакция

Списание ставки в `casino/server.js`:

```js
const res = await dbRun(
  "UPDATE users SET balance = balance - ? WHERE id=? AND balance >= ?",
  [amount, userId, amount]
);
if (!res.changes) return false; // денег не хватило
```

Условие `AND balance >= ?` — ключевое. Оно не даёт уйти в минус даже при
одновременных запросах. Проверка «прочитал баланс → потом списал» опасна: между
чтением и записью баланс может измениться.

Для составных операций есть `withTx`:

```js
await withTx(async () => {
  // BEGIN IMMEDIATE
  await dbRun("UPDATE users SET balance = balance - ? WHERE id=? AND balance >= ?", ...);
  await dbRun("INSERT INTO withdrawals ...");
  await dbRun("INSERT INTO transactions ...");
  // COMMIT
});
```

`BEGIN IMMEDIATE` сразу берёт блокировку на запись, поэтому два параллельных
списания не пройдут одновременно.

### 5.3. `transactions` — журнал, а не украшение

Любое изменение баланса пишет строку: кто, сколько, тип, описание, время.
Это нужно для:

- истории игрока;
- разбора спорных ситуаций;
- статистики;
- отладки («почему у игрока минус?»).

Типы: `bet`, `win`, `deposit`, `hold`, `refund`, `admin`, `promo`, `transfer`.
Названия не случайны — по ним строится история в UI.

## 6. Комната как конечный автомат

В `casino/server.js` класс `Room` хранит всё состояние партии:

```js
this.status = "waiting";   // waiting → playing → finished
this.players = new Map();
this.deck = [];
this.table = [];
this.currentTurn = null;
this.betsReserved = false;
this.settled = false;
```

### 6.1. Три состояния

| Состояние | Что происходит | Кто может действовать |
|---|---|---|
| `waiting` | комната создана, ждём игроков | создатель: добавить бота, начать |
| `playing` | ставки списаны, идёт партия | игроки по очереди |
| `finished` | победитель определён, приз выплачен | создатель: реванш |

Переходы должны быть явными. Если разрешить `startGame` в `finished`, игроки
заплатят дважды. Поэтому в обработчике стоит проверка:

```js
if (room.status !== "waiting") return;
```

### 6.2. Ставки: сначала списать, потом играть

`startRoom()`:

1. Проверяет, что игроков достаточно.
2. Списывает ставку у каждого (`tryDeduct`).
3. Если у кого-то не хватило — возвращает уже списанные ставки.
4. Меняет статус на `playing`.
5. Сохраняет и рассылает состояние.

Это классическая схема «резервирование средств». Альтернатива — списывать в конце,
но тогда игрок может выйти с пустым балансом и всё равно получить приз.

### 6.3. Ходы

Каждая игра реализует свою функцию:

```js
if (room.gameType === "blackjack") error = handleBlackjackAction(room, player, action);
else if (room.gameType === "durak") error = handleDurakAction(room, player, action, cardId);
else if (room.gameType === "dice") error = handleDiceAction(room, player, action);
```

Функция возвращает `null` при успехе или строку с ошибкой. Это удобно: обработчик
сокета не разрастается в сотни строк.

Внутри каждой функции — три обязательные проверки:

1. **Игра идёт?** `room.status === "playing"`.
2. **Это ход игрока?** `room.currentTurn === player.id`.
3. **Действие допустимо?** Не бросал ли уже, есть ли такая карта, не перебор ли.

### 6.4. Таймауты

Если игрок отключился или думает слишком долго, партия не должна висеть вечно.
`scheduleTurn(room)` ставит таймер на `MOVE_TIMEOUT` секунд. По истечении:

- в блэкджеке игрок автоматически получает «пас»;
- в костях бросается кубик за него;
- в дураке выполняется безопасный авто-ход.

Таймер всегда очищается перед новым (`clearTurnTimer`), иначе старые таймеры
начнут менять состояние новой партии.

### 6.5. Завершение и выплата

`settleRoom(room)`:

1. Считает банк: сумма ставок реальных игроков (боты не платят).
2. Вычитает комиссию `COMMISSION_PERCENT`.
3. Делит приз между победителями.
4. Начисляет баланс и пишет `transactions` типа `win`.
5. Ставит `status = "finished"`, `settled = true`.
6. Рассылает `gameFinished`.

Проверка `settled` защищает от двойной выплаты: даже если `settleRoom` вызовется
дважды, второй раз деньги не начислятся.

## 7. Контракт Socket.io

События — это публичный API. Их нужно документировать и не ломать без причины.

### Клиент → сервер

| Событие | Данные | Смысл |
|---|---|---|
| `join` | `{ sessionToken, userId, userName, roomId?, gameType?, bet?, maxPlayers? }` | войти в комнату или создать новую |
| `startGame` | — | создатель начинает партию |
| `addBot` | — | добавить бота (только в `waiting`) |
| `playerAction` | `{ action, cardId? }` | ход игрока |
| `leaveRoom` | — | явный выход |
| `rematch` | — | реванш после `finished` |

### Сервер → клиент

| Событие | Данные | Смысл |
|---|---|---|
| `joined` | `{ roomId, userId, name, isCreator }` | вход подтверждён |
| `roomUpdated` | снимок комнаты для этого игрока | новое состояние |
| `gameStarted` | `{ gameType }` | партия началась |
| `gameFinished` | `{ winner, results }` | итог |
| `balance` | `{ userId, balance, points }` | актуальный баланс |
| `error` | `{ message }` | ошибка действия |

### Почему `roomUpdated`, а не отдельные события на каждый чих

Один снимок состояния проще синхронизировать: клиент не должен собирать состояние
из десяти событий. Пришёл `roomUpdated` — перерисовали экран. Это снижает число
багов «у одного игрока карта есть, у другого нет».

## 8. Сохранение и восстановление

### 8.1. `web_rooms`

Каждое изменение комнаты вызывает `saveRoom(room)`:

```js
INSERT INTO web_rooms (id, state, updated_at) VALUES (?,?,?)
ON CONFLICT(id) DO UPDATE SET state=excluded.state, updated_at=excluded.updated_at
```

`state` — JSON всего состояния. Это не самая нормализованная схема, но для
активных партий она идеальна: одна запись = одна комната, легко восстановить.

### 8.2. Что происходит при перезапуске

`loadRooms()` читает все комнаты из `web_rooms`:

- битый JSON → запись удаляется;
- `finished` старше 15 минут → удаляется;
- остальные → `Room.fromState()` и в память.

После перезапуска игроки могут переподключиться: у комнаты тот же код, состояние
сохранено, ставки уже списаны.

### 8.3. Очистка комнат (важная часть!)

Комнаты — не вечные. Иначе список «активных» превращается в свалку, а память
растёт. В `casino/server.js` есть три уровня защиты:

1. **`isVisible()`** — комната показывается в `/api/rooms`, только если в ней есть
   хотя бы один **онлайн**-игрок. Пустая комната сразу исчезает из списка.
2. **Явный выход** — `leaveRoom(socket)` удаляет игрока; если людей не осталось,
   комната удаляется сразу вместе с записью в SQLite.
3. **Фоновая очистка раз в минуту**:
   - нет людей вообще → удалить через 60 секунд;
   - `waiting` без онлайна → удалить через 2 минуты;
   - `waiting` создана более 30 минут назад → удалить;
   - `finished` старше 15 минут → удалить;
   - `playing`, все офлайн более 10 минут → вернуть ставки и удалить.

Плюс клиент при уходе со страницы игры отправляет `leaveRoom`. Это лечит
классический баг «создал комнату, вернулся на главную, а она висит».

## 9. Вход на сайт по коду из Telegram

Пароли не нужны. Схема:

```
1. Игрок в боте нажимает «🌐 Войти на сайт».
2. Бот создаёт одноразовый код в login_codes (TTL 15 минут).
3. Игрок вводит код на сайте.
4. Сайт меняет код на токен web_sessions (30 дней).
5. Все запросы идут с Authorization: Bearer <токен>.
```

Почему так:

- код одноразовый — перехваченный код нельзя использовать повторно;
- код привязан к Telegram ID — аккаунт тот же, что в боте;
- токен долгий — не нужно вводить код каждый раз;
- бот и сайт используют одну таблицу `users`.

Проверки при входе:

```js
if (row.kind !== "player") return 403;  // админский код не пускаем на игровой вход
if (row.used_at) return 410;            // уже использован
if (row.expires_at < nowSec()) return 410; // истёк
```

Админский вход — отдельный тип кода `kind = 'admin'`, его бот выдаёт только тем,
кто есть в `ADMIN_IDS`. При каждом админ-запросе сессия заново сверяется с
`ADMIN_IDS`: если владелец убрал ID из списка, старый токен перестаёт работать.

## 10. Донаты, выводы и режим «Бизнес/Развлечение»

### 10.1. Донат

Донат — это **заявка**, а не мгновенное начисление:

1. Игрок переводит деньги на карту.
2. Сайт/бот создаёт строку в `deposits` со статусом `pending`.
3. Админ видит заявку и подтверждает.
4. Только после подтверждения начисляется баланс и пишется `transactions`.

Почему не начислять сразу? Потому что сервер не знает, дошёл ли реальный перевод.
Подтверждение админа — единственная точка, где виртуальные монеты появляются из
внешних денег.

### 10.2. Вывод на карту или счёт

Раньше в проекте был «вывод Telegram Premium» — это плохой UX и не деньгами.
Сейчас игрок указывает:

- способ: `card` (карта) или `account` (банковский счёт);
- реквизиты: 16–19 цифр карты или 6–34 символа счёта;
- имя получателя;
- банк (необязательно).

Схема:

1. Игрок создаёт заявку.
2. Сумма **сразу замораживается** (`hold`) — списывается с баланса.
3. Админ видит реквизиты и переводит деньги вручную.
4. «Выплачено» — заявка закрывается, деньги остаются списанными.
5. «Отклонить» — сумма возвращается (`refund`), заявка закрывается.

Реквизиты хранятся в `withdrawals`:

```sql
payout_method TEXT,   -- card | account
payout_target TEXT,   -- номер карты/счёта
payout_name   TEXT,   -- имя получателя
payout_bank   TEXT,   -- банк
source        TEXT    -- site | bot
```

Это позволяет админу видеть в одной панели и сайт, и бота.

### 10.3. Режим работы

В таблице `settings` есть ключ `APP_MODE`:

| Значение | Что доступно |
|---|---|
| `business` | донаты, пополнения, выводы |
| `fun` | только игра, денежные операции запрещены |

Переключается в админке: **/admin → Настройки → Режим работы**. Значение читается
из БД на каждом запросе, поэтому переключение действует сразу и на сайт, и на бота,
без перезапуска.

Где стоит защита:

- `POST /api/donate` → 403 в `fun`;
- `POST /api/withdraw` → 403 в `fun`;
- бот `/deposit`, `/withdraw`, кнопка «Донат» → сообщение о режиме «Развлечение»;
- кнопки пополнения/вывода скрываются из главного меню бота;
- вкладка «Касса» скрывается в навигации сайта;
- страница кассы показывает объяснение вместо форм.

Важно: проверка должна быть **на сервере**, а не только в UI. Скрытая кнопка —
это удобство, а не защита.

## 11. Админка: доступ и действия

Админка — это не отдельный сервер, а REST API с токеном:

```
GET  /api/admin/overview
GET  /api/admin/users?q=...
POST /api/admin/balance
GET  /api/admin/deposits?status=pending
POST /api/admin/deposits/:id/resolve
GET  /api/admin/withdrawals?status=pending
POST /api/admin/withdrawals/:id/resolve
GET  /api/admin/settings
PUT  /api/admin/settings
POST /api/admin/close-room
POST /api/admin/broadcast
```

Каждый обработчик начинается одинаково:

```js
if (!(await requireAdmin(req, res))) return;
```

`requireAdmin` проверяет:

1. `ADMIN_PANEL_ENABLED` — панель вообще включена;
2. токен есть и не истёк;
3. `user_id` из сессии всё ещё в `ADMIN_IDS`.

Пароль — только запасной вход, если `ADMIN_PASSWORD` задан явно. Пароль
`admin123` нигде не является значением по умолчанию.

## 12. Фронтенд: как React разговаривает с бэкендом

### 12.1. Три клиента в `src/lib/api.js`

- `api.anon` — без токена (вход, топы, режим);
- `api.me` — с токеном игрока;
- `api.admin` — с токеном админки.

Токены хранятся в `localStorage` / `sessionStorage`. При 401 игрок разлогинивается.

### 12.2. Общее состояние

`AppContext` хранит:

- `user` — текущий игрок;
- `mode` — `business` / `fun`;
- `notify` — тосты;
- `refresh` — перечитать профиль;
- `refreshMode` — перечитать режим.

Режим обновляется раз в 30 секунд. Этого достаточно, чтобы админ переключил его,
а игроки увидели изменения без перезагрузки.

### 12.3. Socket-клиент

`src/lib/socket.js` создаёт один общий сокет. `GamePage`:

1. На монтировании отправляет `join`.
2. Подписывается на `roomUpdated`, `gameStarted`, `gameFinished`, `balance`.
3. При размонтировании отправляет `leaveRoom` — чтобы не оставлять «мёртвые»
   комнаты.

## 13. Безопасность: чек-лист

- [x] Клиент не присылает баланс и результат — только намерение.
- [x] `sessionToken` важнее `userId` из клиента.
- [x] Одноразовые коды входа с TTL.
- [x] Админ-сессия сверяется с `ADMIN_IDS` на каждом запросе.
- [x] Rate limit на вход, донат, вывод, действия в игре.
- [x] `helmet` + CSP.
- [x] Чужие карты скрываются до конца партии.
- [x] Ставки списываются атомарно (`balance >= amount`).
- [x] Вывод замораживает средства до решения админа.
- [x] Режим `fun` проверяется на сервере.
- [x] SQL-запросы с параметрами (`?`), без конкатенации пользовательских данных.

Чего сознательно нет:

- реального платёжного шлюза (подтверждение вручную);
- полноценной антифрода-системы;
- кластеризации Socket.io (один процесс).

Для учебного проекта этого достаточно; для продакшена добавляйте платёжный шлюз,
Redis-adapter для Socket.io и внешний аудит операций.

## 14. Тесты: как убедиться, что ничего не сломалось

### 14.1. Unit / integration Python

```bash
python tests/run_tests.py
```

Покрывает:

- баланс, ставки, переводы;
- промокоды;
- заявки на вывод с реквизитами;
- заявки на пополнение;
- коды входа;
- настройки и режим `APP_MODE`;
- комнаты в боте;
- рассылки.

### 14.2. E2E веб-сервера

```bash
node tests/web_e2e.js
```

Поднимает настоящий `casino/server.js` на свободном порту с временной SQLite и:

- играет партии в кости, блэкджек, дурак;
- проверяет выплаты;
- логинится по коду;
- проходит донат и вывод;
- переключает режим `business`/`fun`;
- проверяет, что комната без онлайна исчезает из `/api/rooms`.

Перед коммитом запускайте оба набора.

## 15. Как добавить новую игру

1. **Добавьте тип** в `GAME_TYPES` (`casino/server.js`) и `GAMES`
   (`bot/services/games.py` + `src/lib/format.js`).
2. **Опишите состояние** в `Room`: колода, стол, текущий ход, победитель.
3. **Создайте `handleXxxAction(room, player, action, cardId)`**:
   - проверка статуса;
   - проверка очереди;
   - проверка допустимости действия;
   - изменение состояния;
   - возврат `null` или текста ошибки.
4. **Добавьте завершение** — кто победил и как делится банк.
5. **Добавьте UI** в `GamePage.jsx`: экран стола и кнопки.
6. **Добавьте тест** в `tests/web_e2e.js`.
7. **Проверьте очистку**: комната должна удаляться после выхода/таймаута.

Внутри контейнера `start.sh` запускает `python bot/main.py`, а он:

3. запускает бота;
